# CLAUDE.md — Rabih Ops

Context for future Claude Code sessions. Read this before making changes.

## What this is

Rabih Ops is an operations-management app for four businesses:

- **BBQ House** (`bbqhouse`) — restaurant
- **SALT** (`salt`) — restaurant
- **Central Kitchen** (`centralkitchen`) — production kitchen
- **Executive Cleaning** (`cleaning`) — cleaning services

Primary user is Rabih (admin). CEO + branch managers are the other human users. Kitchen/line staff do **not** log in in V1 — they interact only via the WhatsApp bot (Phase 5).

The full product plan lives in `PLAN.md`. Read it before doing non-trivial work. Scope is **locked** — Part 3 lists what V1 does and doesn't include. Don't build beyond it.

## Non-negotiable rules (from `PLAN.md` Part 2)

1. Every mutation goes through a `SECURITY DEFINER` RPC. Zero direct table writes from JS.
2. RLS is enabled on every table. Only `SELECT` policies exist — writes are blocked unless they come through an RPC.
3. No feature ships without a Playwright test covering the happy path + one failure case.
4. No SQL runs in production without 24h in staging first. (Currently staging-only.)
5. Every RPC returns final state (row as jsonb). The caller verifies state; never trust success alone.
6. Every table column has a `COMMENT`. Every RPC has a docstring.
7. Mobile responsive from commit #1 — never retrofit.
8. No secrets in code or in `.env*` files committed to the repo.
9. Pre-commit / CI runs ESLint + typecheck. Don't land broken commits.
10. Feature branches + PR reviews. Never commit directly to `main` once beta users exist (we're pre-beta — direct commits to `main` are still OK for infra bootstrapping).

## Tech stack

- **Frontend**: React 18 + Vite + TypeScript, Tailwind + shadcn/ui components, TanStack Query (with localStorage persister), Zustand, React Hook Form + Zod.
- **Offline**: `vite-plugin-pwa` (Workbox) + `localforage` queue in `src/lib/offlineQueue.ts`.
- **Backend**: Supabase (Postgres + Auth). RLS everywhere. SECURITY DEFINER RPCs only.
- **Routing**: react-router-dom 7.
- **Testing**: Playwright for E2E (`tests/e2e`), Vitest for units (not yet wired).
- **Deployment target** (later): Cloudflare Pages.
- **CI**: GitHub Actions, `.github/workflows/ci.yml`.

## Environment

`.env.local` is gitignored. Required keys:

```
SUPABASE_URL=…                  # staging project URL
SUPABASE_ANON_KEY=…             # public anon key
SUPABASE_SERVICE_ROLE_KEY=…     # service role (scripts only, NEVER shipped to client)
SUPABASE_ACCESS_TOKEN=…         # personal access token for Management API
SUPABASE_PROJECT_REF=…          # staging project ref (also works for prod when we have one)
APP_ENV=staging
TELEGRAM_BOT_TOKEN=…            # only set when wiring Phase C
TELEGRAM_WEBHOOK_SECRET=…       # auto-generated by scripts/telegram-setup.mjs
TELEGRAM_INTERNAL_SECRET=…      # auto-generated; used by pg_cron→telegram-tick
VITE_TELEGRAM_BOT_USERNAME=…    # bot username without @, used by Settings card to build the t.me deep-link
GOOGLE_OAUTH_CLIENT_ID=…        # only set when wiring Phase D
GOOGLE_OAUTH_CLIENT_SECRET=…    # server-side only
VITE_GOOGLE_OAUTH_CLIENT_ID=…   # same client_id, exposed to frontend (Google says it's public)
RABIHOS_APP_URL=…               # http://localhost:5175 for dev, or production URL — used for OAuth redirect bounce
```

Vite reads `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_APP_ENV`. These are currently duplicated into `.env` (also gitignored). Never use service-role keys in the client.

## Deploying database changes

1. Write a new file in `supabase/migrations/` named `<yyyymmdd>_<slug>.sql`. Use `begin;` / `commit;` and make it idempotent (`create … if not exists`, `drop policy if exists`, etc.).
2. Apply to staging: `npm run db:push`.
3. Verify: `node --env-file=.env.local --experimental-strip-types scripts/db-verify.ts`.

Each migration should:

- Stay inside one transaction.
- Add comments to every new column and function.
- Update RLS and RPCs together when the schema changes — never leave a table with writes enabled but no RPC to drive them.

## Telegram bot (Phase C — live; commands V1)

Schema and RPCs ship in [supabase/migrations/20260518_telegram_module.sql](supabase/migrations/20260518_telegram_module.sql). Two Edge Functions live in [supabase/functions/](supabase/functions/):

- **telegram-webhook** — Telegram POSTs incoming messages here. Validates the secret-token header, parses the command, calls the matching `rpc_telegram_*` RPC, replies via Bot API.
- **telegram-tick** — pg_cron POSTs here every minute via pg_net. Drains pending `channel='telegram'` reminders and, at 06:00 UTC (08:00 Africa/Maputo), fans out the daily summary to admin/CEO linked users.

Commands V1: `/start <token>`, `/today`, `/overdue`, `/waiting`, `/purchases`, `/done <id>`, `/note <id> <text>`, `/task <title> for <branch>`, `/unlink`, `/help`. Short ids are the first 8 hex chars of the task UUID; if the prefix matches multiple open tasks the bot replies "Multiple matches — try more characters".

Reminder backoff: 1m / 5m / 30m. After the 4th attempt fails the row is marked `failed` and audited as `reminder_failed`.

### Setup (one-time per environment)

1. Create the bot via @BotFather. Copy the bot token + username.
2. Add to `.env.local`:
   - `TELEGRAM_BOT_TOKEN=<bot token>`
   - `VITE_TELEGRAM_BOT_USERNAME=<username without @>` (used by the Settings card to build the deep link)
3. Run `node --env-file=.env.local scripts/telegram-setup.mjs`. It generates `TELEGRAM_WEBHOOK_SECRET` and `TELEGRAM_INTERNAL_SECRET`, pushes Edge Function secrets via the Management API, populates `vault.secrets` for the cron job, and registers the webhook with Telegram.
4. Deploy the functions: `supabase functions deploy telegram-webhook --project-ref $SUPABASE_PROJECT_REF` and `... telegram-tick`.
5. In RabihOS → **Settings → Link Telegram** → click the t.me link → bot replies `✅ Linked`.

### Security rules

- Bot token only in Supabase Edge Function secrets — never in repo, never in client bundle.
- Webhook is auth'd via Telegram's `X-Telegram-Bot-Api-Secret-Token` header.
- `telegram-tick` is auth'd via a shared bearer secret stored in Vault; pg_cron reads it via `vault.decrypted_secrets`.
- All Telegram-driven writes go through SECURITY DEFINER RPCs and are audited as `source='telegram'`.

## Google Calendar (Phase D — backend live; OAuth pending Google Cloud setup)

Schema and RPCs ship in [supabase/migrations/20260521_google_calendar_module.sql](supabase/migrations/20260521_google_calendar_module.sql). Two Edge Functions live in [supabase/functions/](supabase/functions/):

- **calendar-oauth-callback** — receives Google's redirect, exchanges code for tokens, writes them via `rpc_calendar_store_tokens` (refresh token goes into `supabase_vault`), 302s the user back to `/settings?google_calendar=connected`.
- **calendar-oauth-revoke** — JWT-auth'd. Looks up the user's refresh token, POSTs to Google's revoke endpoint, calls `rpc_calendar_mark_disconnected`. The Settings "Disconnect" button hits this.

Two more Edge Functions land in chunks 5 and 6: `calendar-list-today` (for the dashboard "Today's calendar" section) and `calendar-create-event` (for the task-detail "Add to Calendar" action).

### Token storage

Refresh tokens live in `supabase_vault` — `google_oauth_tokens` only stores the `refresh_token_secret_id`. Access tokens are stored inline (they expire hourly; refreshed by the Edge Function on demand). The table has RLS enabled with **no SELECT policies** — frontend can never read it; only Edge Functions reach it via service role.

### Setup (one-time per environment)

1. **Google Cloud Console**:
   - OAuth consent screen → External → add scopes `calendar.events`, `userinfo.email`, `openid`.
   - Credentials → Create OAuth 2.0 Client ID → Web application.
   - Authorized redirect URI: `https://<project-ref>.supabase.co/functions/v1/calendar-oauth-callback`.
2. **Add to `.env.local`**:
   - `GOOGLE_OAUTH_CLIENT_ID=<id>`
   - `VITE_GOOGLE_OAUTH_CLIENT_ID=<id>` *(same value; Google docs explicitly say client_id is public)*
   - `GOOGLE_OAUTH_CLIENT_SECRET=<secret>`
   - `RABIHOS_APP_URL=http://localhost:5175` *(or production URL)*
3. **Deploy** (already done): `supabase functions deploy calendar-oauth-callback --no-verify-jwt` and `supabase functions deploy calendar-oauth-revoke`.
4. **Run** `node --env-file=.env.local scripts/calendar-setup.mjs` — pushes the three Edge Function secrets via the Management API.
5. In RabihOS → Settings → **Connect Google Calendar** → consent → bounce back → "Connected as you@gmail.com".

### What V1 does

- Connect / disconnect from Settings (UI + Edge Function flow)
- Today's events on the dashboard *(chunk 5)*
- Add to Calendar from a task's detail page *(chunk 6)*
- Audit verbs: `calendar_linked`, `calendar_unlinked`, `calendar_event_created`, `calendar_event_deleted`

### What V1 does NOT do

- No Gmail
- No two-way sync (Calendar event changes don't flow back into RabihOS)
- No automatic deadline → calendar event sync (manual "Add to Calendar" only)
- No follow-up → calendar (schema is polymorphic so V2 just turns it on)
- Primary calendar only (no calendar selection)
- No meeting → follow-up

## Things to avoid

- Adding libraries not already in `package.json` without reading `PLAN.md` Part 4 first.
- Touching production (no prod project exists yet — staging only).
- Adding direct table inserts/updates/deletes from the client. Always a new RPC.
- Committing `.env`, `.env.local`, or anything containing `sbp_`, `sb_secret_`, or `eyJ…` JWTs.
- Expanding V1 scope (see Part 3 LOCKED list).
